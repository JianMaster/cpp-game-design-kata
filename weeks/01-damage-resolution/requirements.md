# Week 01 — 伤害结算 / ダメージ処理

## 目标 / 目的

训练把简单游戏规则在写代码之前转换成具体、可实现设计的能力。  
単純なゲームルールを、コーディング前に具体的で実装可能な設計へ落とし込む能力を鍛えます。

这个问题故意设计得很小。**不要扩展成完整战斗框架。**  
この課題は意図的に小さくしています。**完全なバトルフレームワークへ拡張しないでください。**

## 需求 / 要件

实现一个简单的 RPG 风格伤害结算模块。  
シンプルな RPG 風のダメージ処理モジュールを実装します。

一个角色拥有 / キャラクターが持つもの：

- 当前 HP / 現在 HP
- 最大 HP / 最大 HP
- 攻击力 / 攻撃力
- 防御力 / 防御力
- 根据 HP 推导出的存活 / 死亡状态 / HP から導かれる生存・死亡状態

一次攻击包含 / 1回の攻撃に含まれるもの：

- 攻击者 / 攻撃者
- 目标 / 対象
- 基础伤害倍率 / 基本ダメージ倍率
- 是否暴击 / クリティカルかどうか

伤害规则 / ダメージルール：

1. 原始伤害 = 攻击者攻击力 × 基础伤害倍率。  
   基礎ダメージ = 攻撃者の攻撃力 × 基本ダメージ倍率。
2. 暴击时再乘以 `1.5`。  
   クリティカル時はさらに `1.5` 倍する。
3. 最终伤害 = 原始伤害 − 目标防御力。  
   最終ダメージ = 基礎ダメージ − 対象の防御力。
4. 最终伤害最低为 `1`。  
   最終ダメージの最小値は `1`。
5. 最终伤害作用到目标 HP。  
   最終ダメージを対象の HP に反映する。
6. HP 不能低于 `0`。  
   HP は `0` 未満にならない。
7. 已死亡的目标不能被攻击。  
   死亡済みの対象には攻撃できない。
8. 已死亡的攻击者不能发动攻击。  
   死亡済みの攻撃者は攻撃できない。

## 验收条件 / 受け入れ条件

至少验证以下情况 / 少なくとも以下を確認すること：

- 普通攻击 / 通常攻撃
- 防御力减少伤害 / 防御力によるダメージ軽減
- 最低伤害为 1 / 最小ダメージが1
- 暴击 / クリティカル
- HP 最低为 0 / HP が0未満にならない
- 死亡攻击者的攻击被拒绝 / 死亡した攻撃者の攻撃を拒否
- 对死亡目标的攻击被拒绝 / 死亡した対象への攻撃を拒否

可以使用 `assert` 或简单测试程序。若还不熟悉测试框架，本周不要为了测试框架增加额外复杂度。  
`assert` または簡単なテストプログラムで構いません。テストフレームワークに不慣れなら、今週はその導入自体を目的にしないでください。

## 限制 / 制約

- 使用 C++17 或更高版本。  
  C++17 以上を使用する。
- 核心领域类型大约控制在 2～5 个。  
  主要なドメイン型は2～5個程度にする。
- 不加入 UI、游戏引擎、渲染、ECS、序列化、网络、事件系统、Factory、依赖注入、数据驱动配置。  
  UI、ゲームエンジン、描画、ECS、シリアライズ、ネットワーク、イベントシステム、Factory、DI、データ駆動設定は追加しない。
- 当前需求没有明确必要性时，不使用继承。  
  現在の要件で必要性を説明できない継承は使わない。
- 不为未来的技能、Buff、属性、装备、联网等需求提前设计通用框架。  
  将来のスキル、Buff、属性、装備、ネットワーク等を想定した汎用フレームワークを先に作らない。

## 本周 C++ 重点 / 今週の C++ ポイント

你需要能够解释 / 説明できるようにすること：

- 为什么参数使用值、引用或指针。  
  なぜ引数を値・参照・ポインタで渡すのか。
- 为什么某个位置需要或不需要 `const`。  
  なぜその場所に `const` が必要 / 不要なのか。
- 为什么使用 getter，为什么修改状态需要通过方法。  
  なぜ getter を使い、状態変更をメソッド経由にするのか。
- 是否真的需要任何指针。  
  本当にポインタが必要なのか。
- 每个对象拥有什么数据，为什么。  
  各オブジェクトがどのデータを所有し、なぜそうするのか。
- 对象之间是否存在所有权关系。  
  オブジェクト間に所有関係があるのか。

本周不考察高级 C++ 技巧。简单但有明确理由的 C++，比复杂但说不清原因的写法更好。  
今週は高度な C++ テクニックを評価しません。複雑だが説明できないコードより、単純で理由を説明できるコードを優先します。

## 写代码之前 / コーディング前

先完成 `design.md`，并单独提交一次。  
先に `design.md` を完成させ、独立したコミットとして残してください。

建议提交顺序 / 推奨コミット順：

1. `week01: add initial design`
2. `week01: implement damage resolution`
3. `week01: refactor after implementation`
4. `week01: add retrospective`

这样周末复盘时可以比较“最初设计”和“最终实现”。  
これにより週末の振り返りで「初期設計」と「最終実装」を比較できます。
