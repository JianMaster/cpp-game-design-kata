# C++ 游戏系统设计训练 / C++ ゲームシステム設計トレーニング

这个仓库专门用来训练：把一个游戏系统需求，转换成可以真正落地实现的 C++ 设计。  
このリポジトリは、ゲームシステムの要件を、実際に実装可能な C++ 設計へ落とし込む能力を鍛えるためのものです。

训练重点不是背设计模式，也不是做大型 Demo，而是反复练习同一条转换链。  
重点はデザインパターンの暗記や大規模 Demo の制作ではなく、次の変換プロセスを繰り返し練習することです。

**需求 / 要件 → 执行流程 / 実行フロー → 状态变化 / 状態変化 → 职责划分 / 責務分担 → 接口设计 / インターフェース設計 → 实现 / 実装 → 重构 / リファクタリング → 复盘 / 振り返り**

## 训练规则 / トレーニングルール

1. 每周只做一个小型游戏系统问题。  
   毎週、小規模なゲームシステム課題を1つだけ扱います。
2. 写代码前，必须先完成当周的 `design.md`。  
   コーディング前に、その週の `design.md` を必ず完成させます。
3. 第一版设计尽量小，不要为了“以后可能会有的需求”提前增加抽象。  
   初期設計は小さく保ち、将来あるかもしれない要件のために先回りして抽象化しません。
4. 除非问题本身确实需要，否则核心领域类型尽量控制在 3～5 个。  
   必要性が明確でない限り、主要なドメイン型は3～5個程度に抑えます。
5. 不要用 `Manager`、`System`、`Service`、`Controller`、`Factory` 这些名字来掩盖没有想清楚的职责。使用时必须解释具体职责。  
   `Manager`、`System`、`Service`、`Controller`、`Factory` という名前で曖昧な責務を隠さないこと。使う場合は具体的な責務を説明できるようにします。
6. 第一版只实现满足验收条件的最小方案。  
   最初の実装は受け入れ条件を満たす最小構成にします。
7. 实现完成后，把最终代码和最初设计进行对比，再填写 `retrospective.md`。  
   実装後、最終コードと初期設計を比較してから `retrospective.md` を記入します。
8. 可以让 AI 检查推理、指出遗漏、挑战设计，但在完成自己的设计之前，不要直接让 AI 给出完整实现。  
   AI に推論の確認、抜け漏れの指摘、設計への反論を依頼して構いません。ただし、自分の設計を作る前に完全な実装を出させないこと。

## C++ 训练重点 / C++ の重点

除了系统设计，每周还会刻意训练 1～2 个和游戏开发求职相关的 C++ 工程能力。  
システム設計に加えて、日本のゲーム開発職を意識した C++ の実務能力も毎週1～2項目ずつ扱います。

- 值 / 引用 / 指针语义 — 値 / 参照 / ポインタの意味
- `const`
- RAII
- 所有权与生命周期 — 所有権とライフタイム
- STL 容器 — STL コンテナ
- 继承与组合的取舍 — 継承とコンポジションの使い分け
- move semantics
- 测试 — テスト
- 动态分配 — 動的メモリ確保
- 基础性能意识 — 基本的なパフォーマンス意識

## 什么才算“进步” / 何を「成長」とみなすか

代码写完不等于进步。  
コードを書き終えただけでは成長とは判断しません。

- 从需求到可实现设计的时间是否缩短。  
  要件から実装可能な設計に到達するまでの時間が短くなったか。
- 执行流程是否完整。  
  実行フローを漏れなく整理できたか。
- 是否识别状态变化和失败路径。  
  状態変化と失敗・拒否経路を認識できたか。
- 职责与数据所有权是否清楚。  
  責務とデータ所有権が明確か。
- 接口是否足够，同时没有过度设计。  
  インターフェースが十分で、かつ過剰設計になっていないか。
- 最终实现与初始设计的差距是否缩小。  
  最終実装と初期設計の差が小さくなっているか。
- 大规模返工是否减少。  
  大きな手戻りが減っているか。
- C++ 的语义选择是否有明确理由，并能解释。  
  C++ の設計判断に明確な理由があり、自分の言葉で説明できるか。

长期目标：面对陌生的游戏系统需求时，不再卡在“我大概知道架构，但不知道第一行怎么写”，而是能较快推导出小而合理、真正可编码的详细设计。  
長期目標は、未知のゲームシステム要件に対して「大まかな構成は分かるが、最初の一行が書けない」という状態を抜け、短時間で小さく妥当な実装可能設計まで落とし込めるようになることです。
